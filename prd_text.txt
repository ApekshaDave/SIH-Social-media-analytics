1. Overview
1.1 Problem
simultaneously infer sentiment, demographics, trending topics, and influence flow across platforms to
produce real audience intelligence  not just engagement counts.
1.2 Goal
Build a working prototype demonstrating five integrated modules (data pipeline, sentiment inference,
demographic profiling, trend detection, network analysis), unified into a single analyst dashboard.
1.3 Target Users
Phase 1 (primary focus): Analysts and researchers - National security & intelligence analysts, policy
researchers. Full-access dashboard.
Phase 2 (later expansion): General public - logged-in users who can view a simplified, view-only version of
the dashboard.
1.4 Build Priority
Mock login flow (to show the auth concept without blocking on real backend auth)
Real authentication + role-based access
Simplified public-facing dashboard view (Phase 2 - only after analyst dashboard is solid)
The general public view is explicitly not a Day 1 priority. It exists in the plan to show scalability/vision, but the
team should not spend build time on it until the analyst dashboard is fully working.
2. Architecture Principle: Strict Separation of Concerns
This is the most important structural rule for the prototype. The system is split into three independent
layers that communicate only through defined interfaces (APls). No layer should directly depend on another
ayer's internal code.

3.3 Ul/UX Design Requirements (Dashboard)
Structure: Multipage, not a single scrolling page. Each module gets its own dedicated page/route so the
interface stays focused and uncluttered:

Design principles:
Minimal: Each page shows only what's needed for that module - no dense walls of data, no unnecessary
panels. Prioritize whitespace over cramming.
Interactive: Charts should respond to hover/click (e.g., hovering a sentiment spike shows the driving posts;
shared" next to a stat, not just a bare number). Avoid jargon-only labels on the Ul itself - save technical
terms for the pitch, not the interface.
Bright, clear color palette: Use a vibrant but purposeful palette - one accent color per module (e.g.,
can jump between modules in one click.

3.5 User Roles & Authentication (Cross-Cutting)
Authentication touches all three layers but should be built as a thin layer on top of the existing separation
 not woven into it.

How this stays separated:
Data layer: A[users table (id, email, password hash, role)  completely separate from the social media data
tables
Backend layer: An auth service (/api/auth/login], [
/api/auth/signup) issuing JWT tokens. Every other
endpoint checks the token's role before returning data  analyst-only endpoints reject public-role tokens
Frontend layer: A login screen + route protection (public users simply don't see analyst-only components),
nothing role-specific baked into the dashboard's data-fetching logic itself
Recommended build order (respecting "dashboard first"):
Build the dashboard against mock data with no login (fastest way to get something demoable)
Once dashboard works, add a simple login screen with hardcoded/mock users (no real backend auth yet)
just to show the flow
If time remains, wire up real JWT authentication with the users table and role-based endpoint checks
This way, if you run out of time, you still have a fully working dashboard demo - authentication becomes a
'nice add-on we also built" rather than a blocker for your core deliverable.
4. Why This Separation Matters for Your Team
With 6 people working in parallel over 36 hours, this structure prevents the most common hackathon failure
 one person's changes breaking another's code right before the demo.
Data person can build and seed the database independently

anyone writes real code. Everyone builds against that contract, not against each other's in-progress code

6. Non-Functional Requirements
Privacy: Demographic inference must be aggregate and anonymized  no individual identification
=== PAGE 7 ===
Modularity: Each of the 5 modules must be independently runnable/testable
Demo reliability: System must work fully offline using seed data, in case live APl access fails during the demo
7. Out of Scope (for 36-hour prototype)
Full production-scale Kafka/Kinesis streaming (mention in pitch, not required in build)
Full Elasticsearch integration (optional; basic PostgresQL search is acceptable)
Complete Cl/cD pipeline (basic GitHub Actions test run is sufficient to demonstrate the concept)
Multi-language sentiment support beyond English/Hindi (mention as future work)
